# Implementation language: Rust

`dsp-cli` is implemented in Rust. The decision optimises for single-binary distribution, fast startup latency,
alignment with DaSCH's existing Rust adoption (dsp-repository, dsp-meta),
and clean isolation from dsp-tools (a different language reinforces ADR-0004's boundary against accidental code sharing).

## Considered alternatives

- **Python.** Rejected — distribution pain is the very thing dsp-tools users complain about;
  100–300 ms cold-start hurts AI-agent loops that make several short-lived calls per session;
  same-language proximity to dsp-tools would invite the "let's just import dsp-tools" anti-pattern that ADR-0004 closes.
- **Go.** Rejected — comparable distribution story to Rust but no DaSCH adoption; introducing a new ecosystem to the org just for this is a poor trade.
- **TypeScript / Deno.** Rejected — Deno is a niche skill within DaSCH (Node + Angular is the frontend stack);
  a Node-based CLI regresses distribution to "install Node + npm install".
- **Scala.** Rejected — JVM startup latency is hostile for short-lived CLI invocations; native-image is fiddly;
  wrong tool for this job despite being DaSCH's deepest engineering bench.

## Consequences

- Distribution is via a single static binary. Specific channels (crates.io, Homebrew tap, GitHub releases, Nix flake) are deferred until they're needed;
  the personal-project phase only requires `cargo install --git` or a local build.
- Likely landing in the `dsp-repository` Cargo workspace if `dsp-cli` is adopted by DaSCH.
  Keep dependencies modular and the crate layout clean so that migration is mechanical,
  not a rewrite. (Now a recorded decision — see ADR-0014.)
- The Rust contributor pool inside DaSCH is smaller than Python's today but growing;
  the small surface of `dsp-cli` (v1: three noun-groups, two verbs) means onboarding cost for a Rust-newcomer is bounded.
- Strategic intent: `dsp-cli` began as a personal exploratory project (initially a private `balduinLandolt/dsp-cli` repo)
  and now lives in the `dasch-swiss/dsp-incubator` prototype playground.
  If it proves valuable, it migrates to a permanent `dasch-swiss/` home — most likely as a crate inside the `dsp-repository` Cargo workspace.
  This shapes early decisions (modular structure, no hard-coded personal config) but does not require dasch-swiss stakeholder approval at this stage.
