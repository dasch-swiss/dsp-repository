# Embedded end-user documentation via `dsp docs`

`dsp-cli` embeds its end-user documentation in the binary at compile time and exposes it through a top-level `dsp docs <topic>` command.
Documentation is structured by **intentional concept**, not by CLI command shape — so the topics complement `--help` rather than duplicating it.
Version sync is automatic because docs ship with the binary; a future docs website can be generated from the same markdown files.

## The three documentation categories

`dsp-cli` produces three kinds of documentation, with distinct audiences and distinct homes:

| Category | Audience | Lives in | Surfaced via |
|---|---|---|---|
| ADRs (decision records) | contributors, future-maintainers | `docs/adr/` | git / GitHub browse |
| Developer documentation (README, contributing guide, build/test) | contributors | repo root + `docs/dev/` | git / GitHub browse |
| End-user documentation (conceptual, crosscutting) | users + AI agents | `docs/topics/` | `dsp docs <topic>` |

**Only the third category is exposed via `dsp docs`.** ADRs and dev docs are contributor artefacts and would actively mislead an end-user agent reading them as guidance.

## Boundary rule between `dsp docs` and `--help`

- **`--help`** answers *what does this command do? what flags does it have?* — per-command, generated by clap.
- **`dsp docs <topic>`** answers *what is this concept? why does the CLI work this way? when should I use X vs Y?* — crosscutting, conceptual.

A doc topic that would just be the long version of a `--help` text does not belong in `dsp docs`. The valuable topics are the ones with no single command to attach them to.

## v1 topic catalog

> **Amendment (2026-06-09, plan 018):** the catalog is expanded from 6 to **9 topics**.
> The original six were *orienting* (they describe the world) but none teach an agent how
> to *operate* it — and design principle 3 (agent-mediated chaining, no session state)
> means the agent must compose the stateless commands itself, which `--help` does not
> teach. Three operational topics — `workflows`, `identifiers`, `errors` — close that gap.
> The would-be `limitations` topic is folded into `dsp-cli`; the browser-token-harvest
> flow is folded into `connecting` (a section, not a standalone topic).

| Topic | Purpose |
|---|---|
| `dsp-cli` | What this CLI is, who it's for, the AI-agent-first design philosophy, key principles (prose by default, agent-mediated chaining, no implicit state), and the v1 limitations (schema-side read-only; one server-wide dump slot; `structure` omits reused-from-sibling link fields). |
| `dsp` | What the DaSCH Service Platform is. VRE vs Repository. What DSP-API exposes and why it's verbose. Just enough orientation for someone new to DSP. |
| `concepts` | The domain vocabulary: project, data-model, resource-type, field, value, value-type, built-in, representation. End-user form of `CONTEXT.md`. Includes the "we say data-model where DSP-API says ontology" mapping. |
| `connecting` | High-level auth + environments model. Why there's no default server. How `.env` is loaded. The auth-state disclosure. The browser-token-harvest flow (read `localStorage.ACCESS_TOKEN`, feed via `DSP_TOKEN` / `dsp auth set-token`). (Flag-level details remain in `--help`.) |
| `output` | The output philosophy: prose by default, structured formats for piping, the JSON envelope, stdout-vs-stderr, the auth-state disclosure footer. (Per-format flag details remain in `--help`.) |
| `dsp-tools` | When to use `dsp-cli` vs `dsp-tools`. End-user form of ADR-0004's boundary rule. **Deliberately brief** — a signpost, not a tutorial. |
| `workflows` | *(added)* End-to-end command-chain playbooks: how to compose the stateless commands (read output A → extract an identifier → build command B). The agent's how-to-chain reference. |
| `identifiers` | *(added)* How to name things across commands: the three-way project identifier (shortcode/shortname/IRI), name-or-IRI for data-models and resource-types, CURIEs, IRIs/ARKs, and how to lift identifiers from output. |
| `errors` | *(added)* The diagnostic contract: exit codes (0/1/2/3), the stable `error.kind` values, and per-kind recovery. End-user/agent form of ADR-0012. |

Topics explicitly *not* included: anything that mirrors a single command's behaviour (would duplicate `--help`).

## Commands

```
dsp docs                  # lists topics with one-line descriptions
dsp docs <topic>          # prints the topic to stdout (raw markdown)
dsp docs <topic> --pager  # pages output (optional; agents typically don't want this)
dsp docs -j               # machine-readable JSON topic index
```

> **Amendment (2026-06-12, plan 020 step 6):** `dsp docs -j` emits the standard
> JSON envelope with name+summary for every topic:
>
> ```json
> {"_meta": {}, "data": [{"name": "dsp-cli", "summary": "…"}, …]}
> ```
>
> `_meta` is present but **literally `{}`** — no server/auth context applies to
> embedded documentation. `-j` conflicts with the `<topic>` positional and
> `--pager` (clap-level, exit 2); it exists only for the no-arg index form.
> Topic *bodies* are never JSON-wrapped. The plan 018 D1 decision (no `Renderer`,
> no `--format` flag on `docs`) is unchanged; `-j` is a narrow flag on `DocsArgs`
> that writes directly to the injected writer.

Topic resolution is strict-match with a "did you mean" suggestion on miss:

```
$ dsp docs filt
Error: no topic named 'filt'. Did you mean 'connecting'?
Run `dsp docs` to see all topics.
```

Partial matching is rejected — it can silently shadow topics added later.

## Cross-linking from `--help`

`--help` includes a "See also: `dsp docs <topic>`" line **only when** reading that topic genuinely helps interpret the command — not as a blanket cross-reference.
Example mappings:

- `dsp vre project list --help` → `dsp docs concepts`
- `dsp vre resource-type describe --help` → `dsp docs concepts`
- `dsp auth login --help` → `dsp docs connecting`
- (most other commands get no "See also")

Pointers exist to bridge real discoverability gaps, not to satisfy a completeness checkbox.

## Implementation

Markdown files live at `docs/topics/*.md`. Embedding happens at compile time via `include_str!` for individual files, or the `include_dir` crate for the whole directory.
No runtime file access; no separate distribution channel needed; binary size grows by a few KB.

The directory layout:

```
docs/
├── adr/                 # contributor artefacts; not in `dsp docs`
├── dev/                 # contributor artefacts; not in `dsp docs`
└── topics/              # end-user docs; embedded into the binary
    ├── dsp-cli.md
    ├── dsp.md
    ├── concepts.md
    ├── connecting.md
    ├── output.md
    ├── dsp-tools.md
    ├── workflows.md      # added (plan 018)
    ├── identifiers.md    # added (plan 018)
    └── errors.md         # added (plan 018)
```

## Considered alternatives

- **Web-only documentation.** Rejected — agents would need network access; version drift between binary and website is silent and inevitable.
- **`--help` only, no separate docs.** Rejected — `--help` cannot fit conceptual or crosscutting content without bloating into uselessness.
- **Topic-per-command structure.** Rejected (this round of grilling) — duplicates `--help`, gives docs no independent value.
  The valuable docs are the ones with no command to attach to.
- **Expose ADRs via `dsp docs`.** Rejected — ADRs are contributor artefacts; they explain *why we chose this design*, not *how to use it*.
  Reading ADRs as usage guidance would mislead an agent.
- **Partial topic matching** (e.g. `dsp docs aut` matches `auth`). Rejected — silent shadowing risk when topics are added.

## Consequences

- `docs/topics/` becomes a versioned part of the source tree; every PR that changes user-facing behaviour considers whether a topic needs updating.
- A future docs website (when/if we publish) is *generated* from `docs/topics/*.md`; the embedded version stays canonical.
- The binary embeds documentation, which is one of its features rather than dead weight — every user gets offline-capable, version-synced docs as part of installing the tool.
- `dsp docs` is a new top-level meta-group alongside `dsp auth`, per ADR-0006. The reserved structure accommodated this without ADR amendment.
- Documentation discipline is now part of the development loop: changing user-facing behaviour without updating relevant topics
  produces stale docs that ship in the very next binary.

## Amendment (2026-08-07, plan 035)

### Topic catalogue: 9 → 10, `sparql` added

A new topic, `sparql`, joins the catalogue (`dsp docs sparql`) — see
[ADR-0016](0016-sparql-passthrough.md) for the command it documents. It carries what `--help` cannot:
the off-by-default availability per deployment, the `--accept` alias table and Fuseki's silent
fallback behaviour, the guardrails (timeout, size caps, concurrency) as the client sees them, the
exit-code contract, the `SystemAdmin` requirement, and the advice to scope queries with an explicit
`GRAPH`. Cross-linked from `concepts` and `workflows`.
