# Embedded end-user documentation via `dsp docs`

`dsp-cli` embeds its end-user documentation in the binary at compile time and exposes it through a top-level `dsp docs <topic>` command. Documentation is structured by **intentional concept**, not by CLI command shape, so the topics complement `--help` rather than duplicating it. Version sync is automatic because the docs ship with the binary.

## The three documentation categories

`dsp-cli` produces three kinds of documentation, with distinct audiences and distinct homes:

| Category | Audience | Lives in | Surfaced via |
|---|---|---|---|
| ADRs (decision records) | contributors, future maintainers | `dsp-cli/docs/adr/` | git / GitHub browse |
| Developer documentation (README, build, test, architecture) | contributors | `dsp-cli/README.md` and `docs/src/dsp-cli/` | git / GitHub browse and the repository book |
| End-user documentation (conceptual, crosscutting) | users and AI agents | `dsp-cli/docs/topics/` | `dsp docs <topic>` |

**Only the third category is exposed via `dsp docs`.** ADRs and developer documentation are contributor artefacts and would mislead an end-user agent that read them as guidance.

## Boundary rule between `dsp docs` and `--help`

- **`--help`** answers *what does this command do and what flags does it have?* It is per-command and generated by clap.
- **`dsp docs <topic>`** answers *what is this concept, why does the CLI work this way, when should I use X rather than Y?* It is crosscutting and conceptual.

A topic that would only be the long version of a `--help` text does not belong in `dsp docs`. The valuable topics are the ones with no single command to attach them to. Anything that mirrors a single command's behaviour is not a topic.

## Topic catalog

The catalog has ten topics. The operational topics `workflows`, `identifiers` and `errors` exist because `dsp-cli` keeps no session state (dsp-cli/ADR-0003): the agent must compose the stateless commands itself, and `--help` does not teach that.

| Topic | Purpose |
|---|---|
| `dsp-cli` | What this CLI is, who it is for, the AI-agent-first design philosophy, key principles (prose by default, agent-mediated chaining, no implicit state), and its limitations (schema-side read-only; one server-wide dump slot; `structure` omits reused-from-sibling link fields). |
| `dsp` | What the DaSCH Service Platform is. VRE vs Repository. What DSP-API exposes and why it is verbose. Just enough orientation for someone new to DSP. |
| `concepts` | The domain vocabulary: project, data-model, resource-type, field, value, value-type, built-in, representation. End-user form of `CONTEXT.md`. Includes the "we say data-model where DSP-API says ontology" mapping. |
| `connecting` | High-level auth and environments model. Why there is no default server. How `.env` is loaded. The auth-state disclosure. The browser-token-harvest flow (read `localStorage.ACCESS_TOKEN`, feed it via `DSP_TOKEN` or `dsp auth set-token`). Flag-level details remain in `--help`. |
| `output` | The output philosophy: prose by default, structured formats for piping, the JSON envelope, stdout vs stderr, the auth-state disclosure footer. Per-format flag details remain in `--help`. |
| `dsp-tools` | When to use `dsp-cli` vs `dsp-tools`. End-user form of the boundary rule of dsp-cli/ADR-0004. **Deliberately brief**: a signpost, not a tutorial. |
| `workflows` | End-to-end command-chain playbooks: how to compose the stateless commands (read output A, extract an identifier, build command B). The agent's how-to-chain reference. |
| `identifiers` | How to name things across commands: the three-way project identifier (shortcode, shortname, IRI), name-or-IRI for data-models and resource-types, CURIEs, IRIs and ARKs, and how to lift identifiers from output. |
| `errors` | The diagnostic contract: exit codes (0, 1, 2, 3), the stable `error.kind` values, and per-kind recovery. End-user and agent form of dsp-cli/ADR-0012. |
| `sparql` | What `--help` cannot carry for `dsp vre sparql query` (dsp-cli/ADR-0016): availability per deployment, the `--accept` alias table and Fuseki's silent fallback, the guardrails (timeout, size caps, concurrency) as the client sees them, the exit-code contract, the `SystemAdmin` requirement, and the advice to scope queries with an explicit `GRAPH`. Cross-linked from `concepts` and `workflows`. |

## Commands

```
dsp docs                  # lists topics with one-line descriptions
dsp docs <topic>          # prints the topic to stdout (raw markdown)
dsp docs <topic> --pager  # pages output (optional; agents typically do not want this)
dsp docs -j               # machine-readable JSON topic index
```

`docs` has no `Renderer` and no `--format` flag. `dsp docs -j` is a narrow flag that writes the standard JSON envelope with the name and summary of every topic:

```json
{"_meta": {}, "data": [{"name": "dsp-cli", "summary": "…"}, …]}
```

`_meta` is present but literally `{}`: no server or auth context applies to embedded documentation. `-j` conflicts with the `<topic>` positional and with `--pager` (clap-level, exit 2) and exists only for the no-argument index form. Topic bodies are never JSON-wrapped.

Topic resolution is strict-match, with a "did you mean" suggestion on a miss. Partial matching is rejected: it can silently shadow topics added later.

## Cross-linking from `--help`

`--help` includes a "See also: `dsp docs <topic>`" line **only when** reading that topic genuinely helps interpret the command, not as a blanket cross-reference. For example, `dsp vre project list --help` and `dsp vre resource-type describe --help` point to `concepts`, and `dsp auth login --help` points to `connecting`. Most other commands carry no "See also". Pointers bridge real discoverability gaps; they are not a completeness checkbox.

## Implementation

The topics are markdown files at `dsp-cli/docs/topics/*.md`, embedded at compile time with `include_str!`, one per topic. There is no runtime file access and no separate distribution channel, and the binary grows by a few KB. The files ship in the published crate (dsp-cli/ADR-0011).

## Considered Options

- **Web-only documentation**: rejected. Agents would need network access, and version drift between binary and website is silent and inevitable.
- **`--help` only, no separate docs**: rejected. `--help` cannot hold conceptual or crosscutting content without bloating into uselessness.
- **Topic-per-command structure**: rejected. It duplicates `--help` and gives the docs no independent value.
- **Expose ADRs via `dsp docs`**: rejected. ADRs explain why the design was chosen, not how to use it, and an agent reading them as usage guidance would be misled.
- **Partial topic matching** (for example `dsp docs aut` matching `auth`): rejected, for the silent-shadowing risk above.
- **A published docs website**: deferred, not rejected. No site exists. If one is published, it is generated from `dsp-cli/docs/topics/*.md` and the embedded copy stays canonical.

## Consequences

- `dsp-cli/docs/topics/` is a versioned part of the source tree. Every PR that changes user-facing behaviour considers whether a topic needs updating; stale topics ship in the very next binary.
- Every user gets offline-capable, version-synced documentation as part of installing the tool.
- `dsp docs` is a top-level meta-group alongside `dsp auth` (dsp-cli/ADR-0006).

Enforced by: the topic files being compiled in with `include_str!` (**structure**); the topic index, strict topic resolution with its "did you mean"
suggestion, and the `-j` index envelope and its flag conflicts by `dsp-cli/tests/docs.rs` and the unit tests in `src/actions/docs.rs`
(**static-analysis**); the boundary between `dsp docs` and `--help`, the "See also" discipline, and keeping topics in step with behaviour, by **review**.
